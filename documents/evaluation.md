# 評価

Astroは、SSG前提。

Astroは、シンプルに利用するべき。

普通のサイトのようにしたいなら、素直に、`laravel-app`, `rails-app`のようなハイブリッドMPAにしたほうがいい。

Astro + cloudflare pagesだと、セキュリティリスクがほとんどなくなるため、シンプルなサイトの場合は、都合がいい。

ただし、+ cloudflare workersになると、コード上のセキュリティリスクが出てくるので、laravel, railsをPaaSで使うときのセキュリティリスクに近づくと思う。

実装例では、+ cloudflare workersで、いろいろ動かしているけど、これが必要な時点で、ハイブリッドMPAにしたほうが無難だと思う。

実装例を、そのまま、まねるのは、非推奨。

## Astroのポジション

静的なサイトだと、丁度いいかもしれないけど、そうでもない部分もある。

なぜなら、Astroを使えるデザイナーやオペレーター（ブログの更新をする人）がいない場合は、あまり、真価を発揮できないから。

Astroに適している条件は、こんな感じ。

- エンジニア向けの静的サイト
- エンジニアが、デザイナーやオペレーターをすればいい程度の静的サイト
- Astroが使えるデザイナーやオペレーターがいる現場

よくよく考えると、Astroのポジションは、かなり限定的だけど、それでいい人にとっては、簡素でいいツールだと思う。

## オペレーターは、非エンジニアが対応するようにもできる

ヘッドレスCMSにすると、オペレーターの部分は、エンジニア以外でも対応可能。

詳しくは、`wordpress-app`参照。

## デザイナーの部分の対応パターン

- デザイナーが、AstroやTailwindに慣れてしまう。
- デザイナーがHTMLで生成したものを、エンジニアが埋め込む

前者ならいいけど、後者はAstroを使う意味があまりないかも。

## + cloudflare workersの許容範囲

- ほとんど、静的なサイト
- ロジックは問い合わせフォームだけ（新たなロジックが追加される可能性がない）
- アクセスが多い
- サーバーの負荷を限界まで減らさないといけない

この場合だけは、Rails,LaravelよりAstroのほうが合理的かも。

ただ、この条件のサイトは、あまりないと思う。

静的なサイトで、アクセスが多いサイトは、あまりないと思う。

もしあるとしたら、何らかのイベント系とかだと思う。

さらに、今は、マシンパワーも上がっているから、よっぽどアクセスが多い場合以外なら、Rails,Laravelでも問題ないことが多いと思う。

静的なサイトがメインの開発会社で、たくさんのサイトを、同じサーバー内で、同時に運用していて、サーバーの負荷が限界になっている場合は、Astroでいいかも。

ただし、この場合でも、システムが若干ごちゃつく代わりに、インフラコストを抑えるという、トレードオフという認識は、持っておかないとまずいと思う。

### トレードオフという認識

```
インフラコストを抑える = システム管理コストが上がる
```

この、トレードオフという視点がないと、間違った技術選択をしかねない。

トレードオフの条件を有利にしたい場合は、上記のように使用条件を厳選すればいいと思う。
